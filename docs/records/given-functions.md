# What the guide says of each function a program gives the library

**Status:** done, 22 November 2026, as step 27 of [`ROADMAP.md`](../../ROADMAP.md), at commit `f5f3d75`, by a session
of Opus 5.5. The session read the guide as step 36 left it, and the code that calls each function: `src/compose.ts`,
`src/engine.ts`, `src/run.ts`, `src/testing/`, and `bridges/react.ts`. What it wrote into the guide is under "What was
written". What waits for the owner is under "For the owner".

## In short

The first table has a row for each kind of function that a user gives the library. It says when the library calls it, how many
times, what it may change or throw, and what becomes of what it returns. A cell names the sentence of the guide that
says it, as `Page: section`, where the section is a heading or the bold title of a rule. A cell marked _code_ says what
the code does where no sentence of the guide does.

The guide already answered most cells. The empty ones were of three kinds:

- **Where a defect is recorded**, for what a parent or an input gives: a child's `external`, a child's `init` started by
  a step, `there`, `key`, `flags`, `ids`, `listening`, an output, a `get` and a `set`. Now described in "Running",
  with a test of each.
- **Which functions are pure.** An `init` that takes flags, a handler of `onEvent`, a `get`, a `set` and an `at` of an
  id are called as freely as `update`: each runs in a parent's `update`, which the testing tools call twice. No
  sentence said they are pure. Now in "Guarantees", "What is left to you", and in the skill.
- **Smaller facts kept by the code and the tests**: a listener that throws leaves the others told; `Host` takes the
  `program`, the `options` and the `fork` of its first render. Now written.

The second table is of a misuse of each function. Every misuse that leaves the library's behaviour not defined is one
that nothing refuses, and each is now in "What is left to you", or waits for the owner. None has a construction that
would refuse it without a cost already weighed and rejected.

## A misuse of each

What a misuse leaves is one of two things. **Defined**: the library behaves as the guide says, and the user is only more
exposed to a bug of their own. **Not defined**: what the guide says of the library rests on the rule that the misuse
breaks. The owner's rule, of 22 November 2026: only a misuse that leaves the behaviour not defined needs a refusal; it
is refused by construction; where that cannot be, by a defect as the program is made; and a rule that nothing checks is
the last resort. A defect in `make` sees the config and at most the first state, so it cannot hold a rule of every
state.

## What was written

Each sentence was checked against the code, and each that no test held got its test first.

- **"Running", "When a defect happens"**: under the table of `where`, a description of where a function that a parent
  or an input gives is recorded. Held by "a defect in a function that a parent or an input gives is recorded where the
  library calls it", thirteen cases in `src/run.test.ts`. `runCommand` itself was held already, by the case
  "runCommand" of "a defect in %s ends the run".
- **"Guarantees", "What is left to you"**, the item on what is pure: an `init` that takes flags, the handlers of
  `onEvent`, the `get` and the `set` of an input, and an `at` of an id, with where each runs. The pages of each say it
  too: "Anatomy of a program", "A program with flags"; "Events and external messages", under "The parent handles an
  event in `onEvent`"; "Inputs", under "The program declares where it goes". So do the skill and the doc comments of
  `Program` and of `onEvent`. Each runs in a parent's `update`: the new test holds it for a child's `init`, a `get` and
  a `set`. An `at` of an id runs where its `get` and its `set` do.
- **"Running", "A listener that throws"**, a description: the others are still told of that state. Held by "defects
  are recorded in the order they happened, and a listener that throws leaves the others told" (`src/engine.test.ts`).
  The doc comment of `subscribe` says it too.
- **"Guarantees", "With the bridge to React, the run lives as long as the effect that starts it"**: `Host` takes the
  `program`, the `options` and the `fork` of its first render, and reads no later ones. The doc comment of `Host` said
  so, and the guide did not. The options and the `fork` were held by tests of `bridges/react.test.ts`; the `program` is
  held by a new one, "shown again by Activity, starts anew the program of its first render".
- **The skill**, "Rules that a test checks": that a model is data, which a test checks on two equal states. The skill
  listed it nowhere.

None of these is a new promise: each is a description, or a rule of the user in "What is left to you", which promises
nothing. So no changelog entry.

## Weighed, and not written

- **When a `set` is called.** The guide says that the library "need not call `set`" where nothing is to be stored. The
  code calls it exactly where the value written is not equal to the one held, and calls `get` once a write. Not
  described: for a `set` and a `get` that keep the rule of a place, when they are called changes nothing that a program
  can see. The one reader it would serve is a `set` that does more, which is not supported. And it is what "A `set`
  free to change the state, promised as the code calls it" (`docs/rejected.md`) would have promised.
- **`Host` and a render that React throws away.** `Host` starts the program in `useState`'s initializer, which React
  calls twice under StrictMode, and once in a render it throws away: an `init` of the flags then runs once more, for a
  program that nothing runs. A description would rest on React's behaviour, which a test of the bridge would have to
  hold, as a premise of the bridge on its renderer (`docs/premises.md`). The rule that an `init` is pure, written here,
  makes it invisible to a program that keeps it, so nothing is written.
- **How many times the functions that say which children are there run.** `ids` runs on the state before and after
  each change. "The library calls them when it chooses" says all that a pure function needs.

## The forms that a doc comment writes

The reader's check of step 36 found the `@param key` of `Rehearsal.hear` writing a child's key without its instance.
The rows of `hear`, `send`, `run`, and of a child's message, command and key, were read against every form that the
doc comments, the skill, the guide and the tutorial write:

- a key: `['Clock', 1, 'ticks']` and `['Row', id, 1, 'ticks']` (`Rehearsal.hear`), `[<child>, instance, key]` and
  `[<child>, id, instance, key]` (`src/compose.ts`), and the same in "Composition", "Testing", "Testing tools" and
  the tutorial;
- a command: `{ _tag: <child>, instance, command }` (`src/compose.ts`), `{ _tag: 'About', instance: 2, command }`
  ("Testing"), and `{ _tag: 'Timer', id, instance, command }` (the tutorial);
- a message: `{ _tag: <child>, message }`, with the `id` and the optional `instance` of an answer
  (`src/compose.ts`, `src/dispatch.ts`, `src/update.ts`), as "Composition" writes it.

All agree with the guide. A comment of `src/log.ts`, `// … its command as { _tag, command }`, leaves out the instance,
but it is a `//` comment on how a message is named by its tags, which the instance does not change.

A check that keeps such forms true is conceivable in two ways. One compiles the `@example` blocks of the doc comments,
as the typecheck compiles the examples: it would not have caught the key of `hear`, since a key is `unknown` there,
and since that key was in a `@param`, not in an example. The other matches the forms with patterns, as
`bun run comments` matches the names of sections: it holds a few forms, and each new form needs a pattern of its own.
Neither is advised: there are five forms, in a dozen places, and a change of one is a change of the API, whose skill
(`change-api`) rereads the comments.

## For the owner

1. **An `Equal` and a `Hash` that keep Effect's laws.** The library compares keys, ids, flags and values written by
   `Equal`, and the guide says what Effect's `Equal` compares by value. It does not say that an `Equal` a program writes
   must keep Effect's laws, equal values having equal hashes among them. Nothing checks one, and a wrong one leaves the
   reconciling of keys and children, the cache of `forwardTo`, and the skip of an equal write not defined. To decide:
   whether "What is left to you" names it, beside "Flags and keys made of values that `Equal` compares by value".
2. **Whether a tool keeps this table**, as `bun run comments` keeps the `guarantees` of the mutations: for instance a
   list of the functions a user gives, read from the declarations, each of which must name a row. Not advised by this
   step: a new function of the API goes through `change-api`, which could ask for its row, at the cost of a line in
   that skill.
