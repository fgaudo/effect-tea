# Change the public API

The API is exactly what [`src/index.ts`](../../../src/index.ts) and
[`src/testing/index.ts`](../../../src/testing/index.ts) export, grouped by concept with a comment per group;
every other module is internal. It is judged on its own terms ("What belongs here" in `AGENTS.md`): argue a
change from the library's concepts, its examples and its users in general, never from what one application
needs.

## Shape it

- One module per concept ("Code" in `AGENTS.md`): a new concept gets a module of its own, and the index
  exports it next to what it belongs with. A testing tool gets a module under `src/testing/`, exported from its
  index.
- Keep the tools symmetric: what `drive` gets, `simulate` and `rehearse` are asked about, and the engine and
  the three tools behave alike where the engine is deterministic ("Invariants the engine keeps").
- Only stable Effect APIs, nothing deprecated, nothing the peer minimum lacks without asking
  ([`upgrade-effect`](../upgrade-effect/SKILL.md)).
- A new entrypoint beside `.` and `./testing` needs the three conditions of `exports` in `package.json`: `bun`
  (the TypeScript source, for consumers that run under Bun), `types` and `default` (`dist/`, for everyone else),
  and an entry in `files` if it is not under `src` or `dist`. The site's `typedoc.json` lists the entrypoints
  too.

## Test it

- A `*.test.ts` next to the module, through behaviour (`run`, `Engine.make`, the public functions), never
  through internals. A guarantee of the README's "Guarantees" is checked by `src/interleaving.test.ts` under
  random orders of clicks, command answers and subscription messages: a new guarantee gets a property there.
- A testing tool's test shows it on a program, and an example's test uses it
  ([`add-example`](../add-example/SKILL.md)): the README's "Examples" table says which tool each example shows,
  and must stay true.

## Document it

In the same change:

- **Doc comments** (`/** */`) on everything the two indexes export: they are the API reference of the
  documentation site, generated by TypeDoc. `cd site && bun install && bun run build` must give no warnings.
  Types the API refers to without exporting them are shown by name only, on purpose (`validation.notExported` is
  off in `site/typedoc.json`).
- **`README.md`**: the concept that uses it in the "Guide", the row of the "API reference" table, and the
  "Testing" section for a testing tool. Every code block uses the current API as it would be written in its
  context (names, signatures, the shape of what it returns), and agrees with the blocks it refers to. Nothing
  checks them: read every block that mentions what changed. The quick start is complete and must run as it
  is; this extracts and runs it (it logs 0, 1, 2, 3):

  ```sh
  awk '/^## Quick start/{f=1} f&&/^```ts/{g=1;next} g&&/^```/{exit} g' README.md > quickstart.check.ts && bun quickstart.check.ts; rm quickstart.check.ts
  ```
- **The examples** that use it.
- **`CHANGELOG.md`**, under the unreleased version, with the version the change needs
  ([`release`](../release/SKILL.md)): a breaking change says how to upgrade, with the old and the new spelling.

## Check it as a consumer

Besides `bun run typecheck`, `bun run lint` and `bun run test`, check the change as a consumer outside Bun
would see it: the `types` and `default` conditions, and the declarations in `dist/`, whose relative imports
`build.ts` rewrites to `.js`.

1. `bun pm pack` (it builds `dist/` first, through `prepack`) makes `fgaudo-effect-tea-<version>.tgz` at the
   root, ignored by git.
2. Extract it into a scratch project outside the repository, with `effect` installed and a `tsconfig.json`
   with `moduleResolution: nodenext`, `skipLibCheck: false` and the `ESNext` and `DOM` libs.
3. Typecheck and run, with Node, code that uses the changed API.
4. Delete the tarball.
